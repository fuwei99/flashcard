## 二、TTS 从硬编码升级为「模板可选 + 逐条传参」

- glue 里 `FC.tts(text, lang|opts)`：第二参从字符串升级为对象，**老写法兼容**。
- opts：`plugin`（缺省=当前选中；`"system"`=系统 flutter_tts）、`voice`、`rate`、`pitch`、`cache`、`extra`（原样并进 JS 插件 `getAudioV2` 的 request）。
- `ttsSeq` 每条可各带参数。
- `TtsService` 按 pluginId 缓存多实例（`Map<String,TtsEngine>`），换插件不重建。

### 落盘三态 cache（默认不落）

| 写法 | 行为 |
|---|---|
| 不传 | 单词跟全局 `ttsWordCacheEnabled`；长句一律流式不落 |
| `cache:true` | 强制落盘 |
| `cache:"name"` / `{name}` | 强制落盘，文件名主干用 name |
| `cache:false` | 强制不落 |

### 缓存命名（肉眼可辨，复用只看 hash）

```
单词：intensive-zh_female_xxx-3f9c1a2b7d40.aac
长句：The quick brown fo-zh_female_xxx-9b2e11aa33cc.aac
      The quick brown fo-zh_female_xxx-9b2e11aa33cc.txt   ← 旁挂全文+参数
```

- 主干 = 自定义 `cache.name` > 文本本身（长文本前 20 字，`_fileSafe` 清洗）
- **复用只看 hash**：`sha1(plugin|text|lang|voice|rate|pitch|extra)`，参数变则新文件，文件名仅给人看

### 豆包路由（bubei_dark 当前约定）

```js
var TTS_WORD     = { plugin: "doubao", voice: "zh_female_wenroutaozi_v2_mars_bigtts", cache: true  };
var TTS_SENTENCE = { plugin: "doubao", voice: "zh_male_cixingjunyu_uranus_bigtts",  cache: false };
var TTS_PASSAGE  = { plugin: "system", cache: false };
```

喂 TTS 的**一直是单词本体，不是音标**（音标字段只显示）。

## 三、语篇挖空 / 切卡并发

- `blankLemmasFor`：只挖「传入那批卡 ∩ 语篇目标词」，已背过的只在语篇划线（`blank:false` → `fc-pw`，不进词库）。`null` = 全挖。通读页不看 blank，整篇划线。

  - 修：`_onMsg` 加 `_handling` 门锁串行化（忙则丢并记日志）；`_load` 改 async + `_mountGen` 世代号，await mountCard 完成，过期 mount 只记日志。

**坑**：CI 有一步 `cp -r templates/. app/assets/templates/`，**真源是仓库根 `templates/`**，`app/assets/templates/` 是构建副本。我先改了副本，一构建就被盖回去。
**修**（`d888f51`）：改动同步回根 `templates/`，三份（本地 / 根 / assets）md5 一致。

**另一个坑**：装新 APK **不会覆盖**手机上的 `Documents/Flashcard/templates/`——`seedPublicTemplates()` 只在目录不存在/为空时铺一次。好处是本地模板永远是你的；坏处是新模板推不下去，得手动改或「重载模板」。

## 六、语篇选词「读成上一个词」根治（`ca864e4`）

**现象**：点 `confirmed` 听到 `secure`、点 `involvement` 听到 `enthusiastic`、点 `resounding` 听到 `rendering`……**恒定慢一拍**。

**根因**：豆包插件是**模块级单例**（`callback` / `ws` / `conn_id` / `step` 全是全局）。
1. `getAudioV2` 一进来 `callback = 新回调`，但上一条的 ws 还在跑；
2. 旧 ws 的音频帧经 `callback.write` 写进了**新会话**；
3. 旧 ws `TTSEnded` 又 `callback.close()` 关掉**新会话**；
4. 新词自己的合成压根没发（`ws != null` → 只 `nextStep()`，而 step 已 3，空转）；
5. 宿主**从没调过插件的 `onStop()`**（契约里明明有），等于零打断。

**修**：
- 插件加 `taskSeq` / `curTask` 任务号，旧任务回调整帧丢弃；`getAudioV2` 先 `ws.cancel()` 旧连接；`onStop` 作废在途任务；`ws.cancel()` 前判空（那堆 `cancel of null` 报错也没了）
- 宿主新增 `JsTtsHost.cancelCurrent()`（叫插件 `onStop` + 关所有 session）
- `JsTtsEngine.stop()` → `host.cancelCurrent()`
- `TtsService._stopAll()` 调 `_lastEngine.stop()` 真打断
- `_speakOne` / `_speakCached` 补 gen 守卫

## 七、例句兜底系统 TTS → 长句真流式（`ca864e4` → `862421e`）

**现象**：例句一直念系统音。

**根因链**：`_speakStreamed` 把引擎的**一次性 Stream** 直接喂 `StreamAudioSource`；just_audio 会对同一 source 多次 `request()`（探测 / 播放 / seek），第二次订阅必炸 `Source error` → `_speakOne` 兜底 `_speakSystem`。

**中间方案（错，已推翻）**：收齐字节 → 临时文件 → 播放。稳是稳了，但**短句也要干等整段合成完**，丢了流式。用户当场否掉。

**最终方案（`862421e`）**：`_EngineStreamSource` 改**可重放中间层**：
- 引擎字节边收边进 `_buffer`，同时实时转发给所有在途订阅 → 真·边收边播，**不收齐**
- 每次 `request()` 新建 controller，先补发 `_buffer` 里 `start` 之后的，再接后续增量 → 二次订阅不再炸
- `_lastSource` 在 `_stopAll` / `dispose` 里释放，取消对引擎流的订阅

一句话：把「只能用一次的管子」换成「带蓄水、谁接都能从任意位置接的池子」。

## 十一、教训

1. **「真源」必须先确认**。CI 有同步步骤时，`assets/` 下的多半是副本；改副本 = 白改。
2. **契约里写了的钩子要真的调**。插件有 `onStop`，宿主从没调 —— 一个「读串」bug 拖了一天。
3. **别用「更稳但更慢」换掉需求**。收齐再播是稳，但把流式需求整个丢了；需求是流式，就老老实实实现可重放流。
4. **单例状态是多任务的天敌**。插件里任何 `callback/ws/step` 全局，只要可能并发调用，就得配任务号。
