## 一、会丢数据 / 会卡的（B 类）

### B-1 · 首次安装点了「允许」，公共目录还是不生效

`DataDir.root()` 的缓存置位写错了地方：

```dart
// 修复前 —— try 之前就置位
_resolved = true;
try {
  ...
  _root = d;
} catch (_) { /* _root 还是 null，但 _resolved 已经 true 了 */ }
```

首次安装时权限还没批，`root()` 必然抛异常 → `_resolved=true` + `_root=null` 被永久缓存。用户点了「允许」，App 里还是私有目录，**必须杀进程重启**才生效。这是那种「用户说不清、你复现不了、但差评一定来」的 bug。

**改法**：`_resolved = true` 挪到 `_root = d` 之后（失败仍可重试），另加 `invalidate()` / `recheck()`。`main.dart` 的 `_askPermission()` 末尾补 `_rebindAfterPermission()`：重新探测 → `_store.rebind()` → `_settings.rebind()` → 补种模板/README → `HotReload.resync()`。

**关键决策**：授权回调里**不缓存失败结果**。`recheck()` 只有拿到目录才往下走，拿不到就当无事发生，下次进 App 还能再试。

### B-2 · 重测轮无限递归（Dart + JS 双端）

`_startMode()` 结尾：`_retestPool` 非空 → `round++; _startMode()`。自递归，而且 `round++` **既不改变 `_retestPool` 也不改变 `_passedModes`**，一旦进了「状态不再变化」的组合就是死循环。

原来的兜底只挡了一种：

```dart
// 只挡「一张考法都没有」的卡
_retestPool.where((c) => _modesFor(c).isEmpty)
```

漏掉的是**更常见的那种**：卡有考法，但用户一个都没开。比如卡只有例句（能考 cloze），而用户在设置里只勾了 choice —— 这张卡永远进不了 `pending`，每轮都被剩下来，`round++` 一路自递归到栈溢出。

**改法两道保险**：

1. 毕业条件放宽为「`_modesFor` 为空 **或** 其考法与启用的 `retestModes` 无交集」；
2. 新增 `const int kMaxRetestRound = 10`，`round >= 10` 时把剩余卡全部放行并 `_nextUnit()`。

**为什么选「放行」而不是「跳过」**：卡在死循环里出不来，比错放几张卡的危害大得多。而且放行只是少考一次，FSRS 那边照常落盘，下次复习还会回来。

`templates/bubei_dark/workflow.js` 里有同构的 `startMode()`（`S.round++` 自递归），**双端都改了**，否则 Web 驱动模式下照样栈溢出。

### B-3 · TTS 闸门被并发 speak 提前放掉

闸门是单个 `Completer` + `??=`：

```dart
void _openGate() => _speakGate ??= Completer<void>();
```

两次并发 `speak` 共用同一个闸门，**先结束的那次就把闸放了** —— 预取立刻恢复，跟还在播的那次合成互相 cancel，反而制造了这个闸门本来要防的串音。

**改法**：引用计数 `_speakGateCount`。`_closeGate()` 先减计数，只有归零才真正放闸；另加 `_forceCloseGate()` 给 `stop()` / `dispose()` 用（那两个场景必须无条件放，不能等计数）。

### B-4 · `purgeCache` 永远删不掉临时文件

清理逻辑是「`dir.list()` 遍历 + 遇到 `.tmp` 就 skip」，但 `.tmp` 是**子目录**，`list()` 非递归 —— 于是主循环根本不会走到它里面，而外层又 skip 了它。临时音频文件只增不减。

**改法**：`purgeCache` 末尾单独清一遍 `.tmp/` 子目录（递归）。顺带在 `init()` 末尾挂了一次 `unawaited(purgeCache(olderThanDays: 7))` —— 以前 `purgeCache` 是个没人调用的死方法。

### B-5 · compact 先清日志，崩了就丢数据

```dart
// 修复前
_writeSnap();          // 快照写完没确认
_logFile.writeAsStringSync('');   // 日志无条件清空
```

中间断电 / 磁盘满 / 写一半被杀 → 快照没落上、日志已清空，**这一段的学习记录全没了**。append-only 的设计前提就是「日志是唯一真相」，先清日志等于把唯一真相先删了。

**改法**：`_writeSnap()` 改为返回 `bool`，`_compact()` 里 `if (!_writeSnap()) return;` —— 快照没落上，日志留着下次重放。

### B-6 · 插件合成无超时，失败回调被吞

两件事：

1. **没有超时出口**。宿主注入的 API 里**没有 `setTimeout`**（`docs/PLUGINS.md` 的 API 表也确认了），插件连上服务端但服务端不回帧时，`nextStep()` 永远停在那一步 —— 上层等不到 `write` 也等不到 `error`，朗读态没有任何出口，只能杀 App。

   → Dart 侧兜：`_Session` 带一个 `Timer?`，`const Duration kSynthesizeTimeout = Duration(seconds: 20)`，到点 `addError` + `close`。

2. **`plugin.js` 的 `ws.on('error')` 会先抛异常**：

   ```js
   console.error(resp.text());   // resp 可能已经消费过，这行 throw
   callback.error(...)            // 于是永远走不到
   ```

   → 加 `try/catch` 安全取 detail；另外 `getAudio()` 里加 `ended` 标志 + `doClose()`/`doError()` 统一收尾，消除「先 close 再 error」的双回调。

**顺带修的**：`_Session` 的 `StreamController` 没注册 `onCancel`。下游（播放端 / just_audio 探测）取消订阅后，`_sessions` 里的条目永远留着，插件还在往一个没有监听者的 controller 里灌 base64（无背压、无界缓冲），`_sessions` 单调增长。→ `onCancel: () => _abandon(id)`。

## 二、性能（C 类）

### C-1 · 懒加载白做了

`book.dart` 的分片懒加载设计是对的：`ch_*.json` 一章一文件，`Chapter` 首次访问才 `readAsStringSync`。

但 `study_plan.dart` 的 `_groups()` 构造 `_Group` 时直接取了 `c.title` / `c.passage` —— **建分组的瞬间就把所有章节全读了**。打开一本 30 章的书 = 读 30 个文件。

**改法**：`_Group` 改为 `const _Group(this.chapter, this.inlineCards, this._title)`，`passage` / `title` 改为懒 getter，`_groups()` 里不再触碰。

### C-2 · 冷启动刷 2000+ 次 prefs

`card_store.dart` 的 `init()` 从 `fromFile` 分支恢复后，末尾无条件调了一次 `_flushPrefs()` —— 把**全量**卡片状态往 `SharedPreferences` 写一遍。prefs 是给「公共目录不可用时兜底」的降级通道，正常路径根本不该写。2000 张卡 = 2000 次同步写，全卡在启动路径上。

**改法**：删掉那次调用。降级通道仍在（状态变更时照写），只是不在启动时全量刷。

### C-3 · 每毕业一张卡重写一次 settings.json

`review_screen` 的循环：

```dart
for (final cid in _session.graduated) {
  _write(cid, ...);
  await s.markDone(card: widget.isCard);   // 每次都 _persist()
}
```

`_persist()` = 重写整个 settings.json + 24 次 prefs 写。一轮 answer 可能同时毕业好几张卡（learn 直接过 + 重测全过），背 20 个词就是 20 次全配置文件重写。

**改法**：新增 `markDoneBy(int n, {bool card})`，循环外合并成一次。

### C-4 · 每次答卡都 fsync

`_append` 的 `writeAsStringSync(..., flush: true)` —— 每答一张卡强制刷盘。日志文件语义上允许丢最后几条（compact 前可重放），不值得为它付 fsync 的代价。

**改法**：`flush: false`。

### C-5 · `reviewDueCount` 建中间 List

```dart
reviewDue.where(...).toList().length   // 为了数个数建个 List
```

**改法**：直接 fold 计数。

## 三、一致性与正确性（D 类）

### D-1 · `FlashCard` 没有 `==`

`Set<FlashCard>` / `contains` / `remove` 全靠引用相等。`_retestPool.remove(c)` 这种操作在卡对象被重建过（重新解析 JSON、热重载）时会静默失败 —— 卡清不掉，每轮都被剩下来，**正好喂给 B-2 那个无限递归**。

**改法**：加 `operator ==`（按 `id` + `templateId`）、`hashCode`（`Object.hash(id, templateId)`）、`toString()`。

> 这两个 bug 是耦合的：D-1 制造了清不掉的卡，B-2 让清不掉的卡变成栈溢出。

### D-2 · 三端遗忘惩罚值不一致（BUG-002 没修完）

BUG-002 只改了 Dart 端（`kForgetRetainExp = 1.5`），漏了另外两份实现：

| 端 | 修复前 | 语义 |
|---|---|---|
| Dart `scheduler.dart` | `s / e^1.5` | 保留 22.3% ✅ |
| Python `core/fsrs.py` | `W[17] if len(W) > 17 else s/2.0` → 实际 `s/2.0` | 保留 50% ❌ |
| Web `webpreview/app.js` | `s / e^2` | 保留 13.5% ❌ |

Python 那份更隐蔽：`W` 只有 17 项（索引 0..16），`len(W) > 17` 恒为 False —— **那是死代码**，实际一直走 `s/2.0`。

后果是用 `core/fsrs.py` 拟合出来的权重，在真机上跑的根本不是同一个算法。

**改法**：Python 加 `FORGET_RETAIN_EXP = 1.5`（注释里写明必须与 Dart 端同步改），Web 端 `Math.exp(2)` → `Math.exp(1.5)`。

**另外加了跨端 golden 自检**：`core/fsrs.py` 的 `__main__` 末尾钉一个断言（S=10 忘记后应得 `10/e^1.5 ≈ 2.2313`），对不上就报「检查与 `scheduler.dart` 的 `kForgetRetainExp` 是否还相等」。这类「三份实现必须同步」的常量，没有断言迟早再漂。

### D-3 · 非法评分静默兜底成 good

两处（`review_screen._onMsg` 和 `webview_bridge` 的 `review.commit`）都是：

```dart
try { rating = Rating.fromKey(key); } catch (_) { rating = Rating.good; }
```

任何拼错的、老模板传的、消息串了的评分，都被当成「**记得**」写进 FSRS —— 永久抬高这张卡的稳定性、把到期日往后推，而且**不报错、不可逆**。

这是调度系统里最危险的一类兜底：它不崩，只是悄悄把数据弄脏。

**改法**：

- `review.commit`：直接返回 `{'ok': false, 'error': '非法评分: "xxx"'}`，让调用方（`workflow.js`）自己决定怎么提示；
- `_onMsg`：写日志后 `return`，**丢弃这条消息** —— 不推进状态、不落盘。

**关键决策**：宁可丢一条消息，也不要记一个错评分。丢消息最多是这一下没反应（用户会再点一次）；错评分是永久污染，而且查不出来。

### D-4 · `build()` 里建 WebViewController

```dart
children: [ if (_ensure() case final c?) WebViewWidget(controller: c) ]
```

`_ensure()` 会 `new WebViewController` + 注册 Channel + `loadHtmlString` —— 三个副作用塞在一个**可能被一帧多次调用**的地方。以前靠 `_controller != null` 的缓存侥幸没事，一旦缓存失效就会重复建控制器、重复 loadHtmlString（还会让同一个 controller 被多个 `WebViewWidget` 持有而报错）。

**改法**：`_ensure()` 返回类型改 `void`，挪到 `initState` 末尾（`setPlan` 之后）调用；`build` 里改成 `if (_controller case final c?)`。

**顺带修的**：`_bridge.messages.listen(_onMsg)` 的订阅句柄没保存，`dispose()` 里也没 cancel —— 回调闭包一直挂在 bridge 的广播流上。改为存 `_msgSub` 并在 `dispose()` 里 cancel。

## 坑与教训

1. **「三份实现」是这个项目的结构性问题**：Dart / Python / Web 各写一份 FSRS，Dart / JS 各写一份会话状态机（B-2 就是双端同构 bug）。改任何一端都要问「另外几份呢」。能加 golden 断言的（D-2）就加，加不了的（B-2）至少要在注释里写明「此处与 XX 同构」。
2. **兜底值要挑安全的方向**。`Rating.good` 作为兜底是错的方向（把数据往不可逆的方向改），`return`（丢弃）才是。同类问题：并发刷新的兜底应该是「丢弃 stale 结果」而不是「谁快用谁」。
3. **「没人调用的方法」不等于「没有 bug」**。`purgeCache` 是个死方法，但一旦有人去调它（本场就调了），里面藏的 `.tmp` 漏删就变成真的泄漏。
4. **缓存置位的位置比缓存本身更容易写错**（B-1）。凡是 `_resolved = true` 这种「一次性开关」，默认应该放在成功分支的最后一行。
