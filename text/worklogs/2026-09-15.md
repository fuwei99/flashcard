## 一、BUG-010 破案：不是玄学，是 WebView 全页重载 + 连击穿透

**体感**：词义页点「下一词」没反应，再点直接越过新卡正面进词义页。

**根因链**：
1. 切卡 = `loadHtmlString(html)` 整页重载，Android 上 100~300ms 白屏/无响应。
2. 无响应期用户自然连击，第二击落点时新页恰好渲染完，正中底部「记得」按钮。
3. 模板脚本刚绑定事件就捕获这记幽灵点击 → `toMeaning("good")` → 正面被秒跳。

**修复（SPA 化）**：
- 骨架页（含模板 CSS+JS+glue）只在会话开始 `loadHtmlString` **一次**。
- 之后每切一张卡：原生 `runJavaScript("window.Flashcard.mountCard(json)")`，DOM 增量替换，无整页重载。
- `mountCard` 内 250ms **连点锁**（`clickLock`），彻底阻断幽灵点击。
- `_onMsg` 只在 `_ready`（onPageFinished）后才允许 `_load`，规避竞态。

**关键转义教训**：`json.encode` 输出已含 `\n` `\"` 等转义，嵌入 JS 单引号字符串时**只许再转义反斜杠与单引号**，加任何其他转义都会在 `JSON.parse` 后被二次反转（`\n` 变真换行、`\"` 变裸引号），直接炸 JSON。已用 Python 模拟链路验证无损往返。

## 八、v0.7.1（`3ece253`）：释义拆两份 + 答错先看错在哪

### 8.1 释义拆两份

卡组里同时存 `meaning`（带短语，只给词义页）和 `meaning_plain`（纯中文，给选词/填空）。
没有 `meaning_plain` 的老数据，代码里自动剥括号兜底：

```dart
static String stripParenthetical(String s) {
  var t = s.replaceAll(RegExp(r'[（(][^（()）]*[)）]'), '');
  t = t.replaceAll(RegExp(r'\s+'), ' ').trim();
  t = t.replaceAll(RegExp(r'[；;、,，]\s*$'), '').trim();
  return t.isEmpty ? s : t;   // 全剥没了就退回原串，宁可留着也别显示空白
}
```

实测效果：

| 原释义 | 剥后 |
|---|---|
| `密集的，加强的；(农业)集约的` | `密集的，加强的；集约的` |
| `盛行，流行；获胜，占优势 (prevail over/against)` | `盛行，流行；获胜，占优势` |
| `遵从，服从；答应，同意 (comply with)` | `遵从，服从；答应，同意` |

### 8.2 答错不再直接跳词义页

`handleChoicePick` 原来是：

```js
if (!isRight) { root.setAttribute("data-state", "back"); playMeaningAudio(); }
```

改成两段式：

- 答错 → **停在原题**，在选中的错误选项上补一行它的中文释义（`revealPickedMeaning`），
  继续按钮文案变「看词义」
- 点「看词义」→ `toMeaning("again")` 进词义页（按 again 计）
- 看完点「下一词」才算真正作答 —— 这张卡后面仍会被重考

### 8.3 答完朗读正确选项

`handleChoicePick` 里统一加 `speak(fields.word)`。
cloze 进卡时仍不自动读（`mode !== "cloze"` 那个判断保留），防泄题。

### 8.4 语篇选词的「当前空」提示改用纯中文

`setActiveBlank` 原来用 `b.meaning`，改成 `b.plain || b.meaning`。

## 九、v0.7.2（`af71cf3`）：填空挖不出空

**用户报**：「一点点词性变化 空就填不了了」

**根因**：`renderCloze` 一上来先 `.replace(/<[^>]+>/g,"")` 把标签全洗掉，
再拿 `fields.word` **原形**去正则匹配。例句里是 `prevailed` / `provoked` / `endorsed`
这种变形，匹配不上 → 空挖不出来 → **整句连答案一起显示**。

而例句里其实**本来就带 `<u>词</u>` 划线标记**（20 张卡全都有），只是被洗掉了。

**用户给的方向**：「你 json 存的例句像语篇一样，把这个词下面划线不就行了，抠的时候直接精准抠掉」—— 完全正确。

**改成三层降级**：

| 优先级 | 策略 | 覆盖 |
|---|---|---|
| 1 | 认 `<u>/<b>/<em>/<strong>` 标记，**整段精准抠掉** | 20/20（现有数据全中） |
| 2 | 无标记 → 原形整词匹配 | 老数据 |
| 3 | 还不行 → 词干 + 后缀白名单（`comply→complied`、`impose→imposed`） | 兜底 |

后缀白名单刻意收窄，避免误伤：

```
"s","es","ed","d","ing","ion","ions","ation","ations","ment","ments","ly",
"ness","er","ers","est","ive","ives","al","ally","ence","ance","ful","less",
"ity","ities","ize","ized","izes","izing","t"
```

验证时特意确认了两个**不能**匹配的反例：
- `act` ↔ `Practice makes perfect.` → MISS（后缀 `ice` 不在白名单）
- `subtle` ↔ `This is a subtitle.` → MISS（后缀 `itle` 不在白名单）

> 词干规则：`y` 结尾且前面是辅音 → 变 `i`（`comply`→`compli`，能匹配 `complied/complies/complying`，
> 但**不会**误match `complete`）；`e` 结尾 → 去 `e`。

## 十、v0.8.0（`629a307`）：卡片格式 v2

### 10.1 用户的两个判断

1. **一词多义 / 一词多性没被考虑** —— 一个 `pos` 字符串 + 一个 `meaning` 字符串塞不下。
   用户建议：不同词义和词性分开存
2. **存储格式和 HTML/CSS 没有扩展性** —— 想加「近义词 / 反义词」难道还要在 json 里
   专门开辟字段？「硬编码从来不是好的选择」。
   用户建议：按 `标题 + 内容` 的格式，可以在下面无限扩展

### 10.2 我修正的那一点（这轮最值钱的决策）

用户说「最简单情况是，按照 标题+内容的格式，可以在下面无限扩展」——
方向对，但**不能一刀切**。我提出的边界是：

> **展示层可以无限扩展，语义层必须固定。**

| | 字段 | 谁读 | 能否扩展 |
|---|---|---|---|
| **语义层（固定）** | `word` `senses` `sentence_en/cn` `phonetic_*` `syllable` | **引擎**：TTS、判分、cloze 抠空、出选项 | ❌ |
| **展示层（扩展）** | `blocks: [{type, title, ...}]` | **模板**：只负责画 | ✅ 无限加 |

为什么 `word` 不能变成 block：cloze 要靠它抠空、TTS 要靠它发音、判分要靠它比对 ——
**这是语义，不是展示**。

### 10.3 `senses`：义项数组

```json
"senses": [
  { "pos": "adj.", "cn": "模糊的；晦涩难懂的；无名的" },
  { "pos": "vt.",  "cn": "使模糊；遮蔽" }
]
```

- 多音词可在义项内带 `phonetic_us`（`record` n./v. 读音不同）
- 老格式（`pos` + `meaning`）在 `FlashCard.senses` 里自动折成一条
- `meaningPlain` 改为**从 senses 现场派生**（剥括号），不再单独存

### 10.4 `blocks`：通用展示块

六种 type，模板**不认识任何业务字段**：

| `type` | 用途 | 数据 |
|---|---|---|
| `pairs` | 短语搭配、词形对照 | `items: [{en, cn}]` |
| `list` | 近义词 / 反义词 / 易混词 | `items: ["a","b"]` |
| `html` | 词根词源、辨析说明 | `html` |
| `text` | 纯段落（转义，安全） | `text` |
| `table` | 词形变化 | `cols`, `rows` |
| `image` | 示意图 | `src`, `alt` |

**未知 type 不崩**：按内容退化渲染（html → 列表 → 表格 → 纯文本）。

`template.html` 里原来硬编码的「常用短语 / 词根词源」两个块删掉，换成一个
`<div class="fc-blocks">` + 一个 `<template id="fc-block-tpl">`。
`script.js` 的 `renderBackFace` 拆成 `renderSenses` / `renderSentence` / `renderBlocks`。

**从此加「近义词」只是往 json 里加一个 block，不动模板、不重编 APK。**

### 10.5 老书兜底

`blocksOf(fields)`：新格式用 `fields.blocks`；没有就现场把老的 `phrases` / `root`
折成 block。所以用户手里的老书不改 json 也能正常渲染。

### 10.6 迁移

`decks/kaoyan_core.json`、`decks/kaoyan_20.json` 迁移到 schema 2（各 20 张卡）。
`obscure` 这种一词多性（`pos: "adj. / vt."`）用 overrides 手工拆成两条义项 ——
字符串里塞多个词性本质上没法可靠自动拆。

## 十五、用户的核心修正：「你目前就是不支持缺失，其实你应该支持缺失」

用户原话拆成四条：

2. **没有例句就不做选择填空，Pass 掉这张卡的该考法就行**
3. **派生词、近/反义词要做成固定卡片，不是 block**；
   近反义词合一张卡；每条**词性+释义绑定**，注意多词性
4. **「短语固定搭配」被写得太刻板化了** —— 有的词压根没有固定搭配，那就不写。
   这个口径要写进 README

### 15.1 为什么派生词 / 近反义词是「固定卡」而不是 block

上一轮我把「加近义词」当成 blocks 的示例（`type: list`）。用户否掉了。

理由站得住：这两类东西的形状是**「词 + 词性释义」绑定**，
需要**专属渲染**（左边词、右边逐条 `词性 + 释义`），
而不是 `list` 那种一行一个字符串。

所以新增三个**固定字段**（顶层，与 `senses` 平级）：

```json
"derivatives": [ {"word": "...", "senses": [{"pos": "...", "cn": "..."}]} ],
"synonyms":    [ ... ],
"antonyms":    [ ... ]
```

渲染：`derivatives` -> 一张「派生词」卡；
`synonyms` + `antonyms` -> **同一张**「近义词 / 反义词」卡，各带小标题。
三个字段都可缺，缺了整张卡不显示（不留空壳）。

宽容读取沿用「双读单写」：`{word, senses}` / `{word, pos, cn}` / `"word"` 三种写法都认。

### 15.2 缺字段最阴的坑：会话死循环

`StudySession` 原本用**全局** `retestModes` 判断一张卡是否毕业：

```dart
bool _allPassed(String id) {
  return retestModes.every((m) => passed.contains(m.key));
}
```

如果一张卡没有例句，cloze 这一关它**永远过不了** ->
`_startMode()` 找不到任何待考卡 -> `_retestPool` 非空 -> `round++` -> 无限重来。

修法：把「考法」从全局改成**按卡过滤**：

```dart
List<StudyMode> _modesFor(FlashCard c) => retestModes.where((m) {
  switch (m) {
    case StudyMode.cloze:  return c.hasSentence;        // 没例句挖不出空
    case StudyMode.choice: return c.senses.isNotEmpty;  // 没词义出不了选项
    default: return true;
  }
}).toList();
```

三处联动：
- `_allPassed(card)` 用 `_modesFor`
- `_startMode()` 的 pending 过滤加 `_modesFor(c).contains(m)`
- `submitLearn`：**一个可用考法都没有的卡直接毕业**，别丢进池子空转
- `_startMode()` 开头再加一道兜底：池里只剩「无可用考法」的卡就放它们毕业

## 十六、这一轮的教训

1. **「可扩展」不等于「什么都塞进 blocks」**。
   blocks 适合「画出来就完事」的展示内容；
   一旦某类内容有**固定语义形状**（词+词性+释义）且**需要专属渲染**，
   就该给它固定字段。上一轮我把近反义词放进 blocks 是判断失误。
2. **缺字段的杀伤力不在渲染，在状态机**。
   模板层「没有就不渲染」很好写；真正会让 App 卡死的是
   **会话编排里一个永远无法通过的考法**。以后加任何「可选字段驱动的考法」，
   都要同时问：**这个字段缺失时，这张卡还能毕业吗？**
3. **校验脚本值得写**。这次它直接扫出 24 处存量脏数据。
