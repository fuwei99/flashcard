# 2026-09-19 · 干扰项归位：从壳里搬回模板

状态：工作区已改，**未 commit**（7 个文件，+101 / -19）。
来源：外部审阅时提出的一个反问 ——「选项是哪四个 · 干扰项现算，这个必须交还给 JS 吧？」

## 本场目标

把「出干扰项」这件事从壳里摘出去，还给模板。

原本这只是一个架构洁癖问题（壳越权定义流程），查下去发现它同时是**性能 bug**
和**死代码**：模板里那份自建池子的代码写好了，但优先级排在第 4 位、还从不预热，
等于白写；而壳那份每次挂卡都要把整本书读进内存。

## 为什么必须交还给模板

**1. 出干扰项要先判题型，题型属于流程。**

`_choicesFor()` 开头两行就是铁证：

```dart
if (step.mode == StudyMode.cloze && !cur.hasSentence) return const [];
if (step.mode == StudyMode.choice && cur.senses.isEmpty) return const [];
```

它已经在读 `step.mode` 了 —— 壳一旦伸手拿「选项」，就顺手把「这张卡考什么」
也攥住了。流程就是这么回流进壳的。

**2. 壳那份顺带把懒加载拆了。**

`Chapter._content` 是懒的（`book.dart:211`）：

```dart
ChapterContent get _content => _loaded ??= (_loader != null ? _loader!() : ...);
```

但 `Book.allCards` 是 `chapters.expand((c) => c.cards).toList()` —— 把每一章的
`cards` 都碰一遍。而 `distractorPool: book.allCards` 在**构造 ReviewScreen 时**
就被求值，于是：

> **打开一章 = 把整本书所有 `ch_*.json` 读进内存。**

`home_screen._poolFromUnits` 里 `for (final c in b.allCards)` 同理，跨书复习时是
多本书一起读。

> ⚠️ 这正是 2026-09-17 修过的 **BUG-019**（「章节懒加载被 `_groups()` 提前触发，
> 打开一本 30 章的书 = 读 30 个文件」）—— **只修了一处，漏了这两处。**
> 同一个病，换了地方复发。

**3. 模板那份是白写的。**

改之前 `distractorCands()` 的优先级是：

```
① 易混项 confusions
② cur.choices        ← 壳塞进来的 ★实际生效
③ S.seenCards
④ _poolByBook        ← 自建整本书池，基本跑不到
```

而 `loadPool` **只在「凑不满 4 个选项」时懒调用**（`script.js:1228` / `:1469`），
从不在会话开始时预热；`distractorCands` 又是**同步**读 `_poolByBook`。
首帧池子必然为空 → 永远在 ② 停下 → 那 50 行读盘代码几乎从不执行。

实测（见下）：冷池时候选数 = **0**。

## 为什么加 `self_distractors` 而不是一刀切

因为 **`bubei_dark` / `bubei_replica` 不会自建池**：

```js
// bubei_dark/script.js:1108
choices = card.choices || [];
```

它们**完全依赖壳下发选项**（0 处 `fs.read` / `loadPool`）。全 5 个模板都是
`web_session: true`，所以「web 驱动」这个信号不足以区分「谁会自己出题」。

于是用 manifest 显式声明，语义是「**我的模板自己出选项，壳别管**」：

| 模板 | `self_distractors` | 干扰项来源 |
|---|---|---|
| `bubei_react_v1` | ✅ | 模板读 `books/<book>/ch_*.json` 自建 |
| `bubei_dark` / `bubei_replica` | ❌ | 仍走壳侧兜底（但已改成惰性） |
| `bubei_ref` / `bubei_build_v1` | ❌ | 同上 |

`bubei_react_v1` 是旗舰模板，所以它先走通。

## 坑与教训

1. **「作者写了注释说要做的事」和「作者实际做的事」可能相反。**
   `ReviewScreen.bookId` 的注释白纸黑字写着「模板据此用 fs.* 自己去读整本书建
   干扰池 —— **壳只给身份，不代劳出题**」，而它上面三行的 `distractorPool`
   正在代劳。**注释是意图，代码是事实，只有代码算数。**
2. **修 bug 要搜同类。** BUG-019 修的是「懒加载被提前触发」，
   但只修了 `_groups()`。同一个 `Book.allCards` 在别处又触发一次。
   凡是「惰性 getter 被谁碰过」这类问题，修完必须全局搜一遍。
3. **兜底值会把主路径挤死。** `cur.choices` 排在自建池前面，加上池子从不预热，
   结果是「写了两份实现，跑的是冗余的那份」。**优先级链里靠前的那个，
   就是事实上的主实现** —— 想清楚谁该是主，就把它排前面，别让它当兜底。

# 2026-09-19（续）· 模板播种收口 + 三层错误捕获

状态：工作区已改，**未 commit**。承接上一场，方向由用户定：

## 一、内置模板改成只带 `bubei_react_v1`

上一场我发现的是「APK 里只有 `bubei_dark`」，当时按 bug 报的；
用户直接纠正了方向：**不是漏了 react_v1，是根本不该带 bubei_dark**。
`bubei_dark` 是早期骨架模板 —— 自己不会算干扰项、数据契约停在 v3，
铺出去就是给用户塞个残废壳。**replace，不是 add。**

| 文件 | 改动 |
|---|---|
| `app/pubspec.yaml` | `assets/templates/bubei_dark/` → `assets/templates/bubei_react_v1/` |
| `app/lib/services/deck_repository.dart` | `_templateDirs` 同上一对一替换 |

CI（`.github/workflows/build-apk.yml:33`）是 `cp -r templates/. app/assets/templates/`，
整目录照搬，所以 **CI 不用动** —— `pubspec.yaml` 的 `assets:` 才是「谁进 APK」的闸门。

### 顺手修掉的连带硬伤：模板改动永远推不到老用户

原播种逻辑是「目录存在且非空 → 整个跳过」。意味着**只要装过一次，
之后所有模板更新都到不了这个用户手上**，只能卸载重装。
对一个「壳只发牌、模板随便热更」的项目，这等于自废武功。

改成逐文件同步 + `.builtin` 标记（内容 `{"id":…, "sha":{文件名:sha256}}`）：

| 情况 | 处理 |
|---|---|
| 目录不存在 | 铺 |
| 有 `.builtin` 标记，文件 sha 对得上记录 | 壳铺的、用户没动过 → 覆盖成新版 |
| 有 `.builtin` 标记，sha 对不上 | 用户改过 → 留着 |
| 没标记、非空 | 用户自己的模板 → 整个跳过 |
| 没标记、空 | 上次铺到一半的残骸 → 接手 |

新增 `staleBuiltinTemplates()`：报告「壳铺过、但已不在内置清单里」的目录
（就是老用户的 `bubei_dark`）。**只报告不删** —— 删用户 Documents 下的东西得用户点头。
结果进 `status.json` 的 `diagnostics.stale_templates`。

## 二、三层全局错误捕获

改之前：整个 `app/lib/` 里 **`FlutterError.onError` / `PlatformDispatcher.onError` /
`runZonedGuarded` / `ErrorWidget.builder` 一个都没有**。build 里抛异常 =
用户看到红屏 + logcat 一行没人看的输出，手机上的用户没法把 logcat 发过来。

### 层 1+2+3：壳（`services/crash_log.dart`，新增）

- `FlutterError.onError` —— build / layout / paint
- `WidgetsBinding.instance.platformDispatcher.onError` —— 引擎层异步异常（返回 `true` 吞掉，
  也就不会重复进 zone handler）
- `main.dart` 的 `runZonedGuarded` —— zone 兜底

落盘 `logs/crash/crash-YYYYMMDD.log` + `last_crash.json`（机器可读）。
**同步写**（崩溃路径上异步写很可能写不完进程就没了）；
目录三级兜底：公共目录 → App 私有 documents → 系统临时目录。
带**去重**（同签名 10s 窗口内只落一次）—— 不去重的话一个 build 死循环
一秒甩几千条、光 fsync 就能把手机卡死，比原 bug 还严重。
`ErrorWidget.builder` 换成一行字的友好页（极简，它自己再抛就是无限递归）。

### 层 4：卡牌页 JS（`TemplateEngine.buildPage`）

**这层是给 card 引擎兜底的主力。** 注入顺序现在是契约：
数据 → glue → **错误钩子** → `script.js` → `workflow.js`。
钩子必须在模板脚本之前，否则模板自身解析期的异常漏掉。

覆盖 `error` / `unhandledrejection` / `console.error|warn` → `FCChannel` → `logs/js/`，
tag 分别是 `JSERR` / `JSPROMISE` / `JSERROR` / `JSWARN`。

**用 `addEventListener` 而不是 `window.onerror = fn`** —— 模板 `script.js` 在本段
之后执行，它要是自己也赋值 `window.onerror` 就会把壳的钩子整个顶掉。
这条专门写了测试。

### 层 4b：WebView 资源错误

`NavigationDelegate.onWebResourceError` 之前没接 —— 模板里的图 / 例句音频 / fetch
挂掉是完全静默的，现象只是「卡上少了一块」。
`review_screen.dart` / `card_preview_screen.dart` 两处补上，走 `logWebResourceError()`。
（`onConsoleMessage` 在 webview_flutter 4.x 已从 `NavigationDelegate` 移除，
要接得走平台特定的 `AndroidNavigationDelegate` —— 不值得，JS 钩子那层已经覆盖了。）

## 坑与教训

1. **我的结论方向和用户的意图可能是反的。** 我看到「APK 里只有 bubei_dark」，
   默认「少了东西 = bug，应该补上 react_v1」；用户的判断是「bubei_dark 根本不该在」。
   同一份事实，两种修法。**报问题时报事实，别顺手替对方定方向。**
2. **「目录存在就跳过」这类幂等守卫，是热更机制的天敌。** 写播种 / 迁移 / 缓存
   填充逻辑时，凡是「已存在就不动」的分支，都要问一句：**那更新怎么推下去？**
   正解不是不覆盖，而是记住「我铺的是哪一版」（这里是 sha），
   靠它区分「我铺的旧版」和「用户改过的」。
3. **注释说要做的事 ≠ 代码做的事**（延续上一场的教训）。
   `deck_repository.dart` 顶部注释写着「首次运行会把内置模板铺一份过去」，
   听着像每次启动都同步，实际是「存在即跳过」。
